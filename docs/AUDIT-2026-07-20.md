## P0 — bugs corrupting the world right now

- [x] **P0.1 — Settlement mood is mathematically pinned negative on
  all four axes.** Live evidence: consciousness prompt shows `hope
  -0.63, fear -0.62, grief -0.61, suspicion -0.67` — four axes that
  should oppose each other, all sitting at the same strong negative.
  Root cause, `settlement/buildings.py::tick_mood`:
  `signal = avg * 2.0 - 1.0` rescales mean agent emotion (0..1) into
  -1..1 — but emotions *decay toward 0* (calm), so a perfectly
  ordinary, calm village produces `signal ≈ -1.0` on every axis, and
  the tracking term drags all four moods toward -1 forever. "Nobody is
  afraid" is being encoded as "profound anti-fear," which is
  meaningless. This poisons every consumer: the consciousness job
  reads a contradictory gloom, narrative themes ("uncertainty, fragile
  hope") are being derived partly from an artifact, and omen/chronicle
  bias inherits it. Fix: map calm to *neutral* — e.g. `signal = avg`
  (0..1 emotion → 0..1 mood, mean reversion pulls to 0, event nudges
  supply the negative range), or track each axis toward
  `avg_of_source − baseline` — and add a migration that re-centers
  existing saved moods. Verify with the emotion-trajectory eyeball
  script from Phase I: a death should spike grief *relative to a ~0
  resting state*, not relative to -0.6.
  **Shipped v1.3.6:** `signal = avg` (no migration needed — mean
  reversion self-corrects existing saved moods over the following
  months).

- [x] **P0.2 — Discourse monoculture: the rumor→memory→dialogue→
  folklore loop has no damping and has collapsed the world's talk into
  one topic.** Measured: in the 500-example pack, topic diversity is
  0.26 and field/soil variants are ~47% of all exchanges; in the older
  session the same run spent an entire year on "Vesna's garden /
  shadows / captured moonlight" (853 rumor events; the chronicle,
  beliefs, town-brain, and folklore prompts in the diagnostics are
  each 60–90% garden lines). The loop: 71% of LLM dialogues emit a
  rumor (142/201 measured) → rumors become memories → memories are
  60% of the next dialogue prompt → folklore condenses the rumors into
  a tale → the tale feeds dialogue/chronicle/dream prompts → repeat.
  Four concrete dampers, all cheap:
  - [x] **(a) Dedupe the pair topic ring.** `Population.record_dialogue_
    topic` appends unconditionally → prompts literally read "You two
    have lately talked about: garden, garden, garden." Skip append
    when `topic` matches the last entry (or normalize + dedupe the
    ring); a run of identical entries defeats the novelty line it
    exists to power.
    **Shipped v1.3.6.**
  - [x] **(b) Gate rumor emission on novelty.** Before spreading a
    dialogue's `rumor`, check it against the settlement's current
    top topic / recent rumor texts (the `top_topics()` machinery is
    already there); an exchange about the dominant topic produces
    conversation but *no new rumor object*. This alone cuts most of
    the 853.
    **Shipped v1.3.6** (`RUMOR_NOVELTY_MIN_COUNT=3` — the leading
    topic must have already recurred a few times before it's treated
    as "dominant," so a settlement's genuinely first topic isn't
    suppressed).
  - [x] **(c) Skip InterpretRumor() on the dominant topic.** 475 of 1,930
    archived examples — 25% of all LLM output — are retellings, mostly
    of the same garden rumor. Spend the 3/day cap only on rumors whose
    topic ≠ the settlement's current dominant one.
    **Shipped v1.3.6** (same gate as (b) — InterpretRumor only fires
    when a rumor was actually spread).
  - [x] **(d) Cap per-category events in `recent_events_diverse`.** The
    live beliefs prompt contains **fourteen** consecutive "Nature
    reclaimed abandoned ground at (x, y)" lines; an institution-belief
    prompt has six. One category should never exceed ~2–3 lines in any
    prompt-bound event slice (the rumor-dedupe-with-echo-count pattern
    from v0.87.5 generalizes directly).
    **Shipped v1.3.6** (`terrain_reclaimed`/`terrain_thinned` added to
    `ROUTINE_EVENT_CATEGORIES` — they were the same bursty
    physical-substrate-tick shape as every category already in that
    set, just never added to it).

- [x] **P0.3 — Construction is starved: 16,662 ticks, population 24,
  ONE standing structure.** Event log: `construction_started: 1`,
  `building_completed: 1`; town-brain prompt confirms `materials
  1.7/30 … 1 standing structures (0 hospitals, 0 schools, 0
  workshops)` while **10 of 25 agents are ill** with no hospital
  buildable. Since founding now deducts materials up-front
  (`MATERIALS_COST_BY_KIND`, hut 3.0 / granary 5.0) *and* workshops,
  repairs, tools, and hospital care all drain the same stockpile, the
  stockpile sits permanently below the cheapest founding cost — sinks
  were added faster than sources. GATHER is one of six goals chosen by
  a model that (see P1.4) reflects its context less than half the
  time, so inflow never wins. Fixes, in order of preference: (i) a
  **civic reservation** — when the town brain's priority implies a
  building and the stockpile is below that kind's cost, a reserved
  fraction of gathered materials is untouchable by workshop/tool/care
  sinks until founding fires; (ii) make the cognition prompt's
  gather-grounding line explicit when `materials < cheapest_needed_
  cost` (the `needs_repair` treatment, again); (iii) re-tune sink
  rates at small populations. Verify with a 5-seed 30k-tick soak
  asserting ≥ N foundings per sim-year at pop ≥ 20 — this is the
  difference between a map that visibly grows and one that never
  changes, which for a game is close to everything.
  **Shipped v1.3.6, scoped to (ii) plus a deterministic-fallback
  counterpart:** new `buildings.cheapest_founding_cost()` +
  `materials_critical` flag threaded into both `cognition.build_
  prompt`'s grounding line AND `fallback_goal` (which is what most
  GATHER decisions actually go through, since only core-cast agents
  reach the LLM path) — when the stockpile can't afford even the
  cheapest kind, GATHER is force-selected the same way hunger/energy
  already force FORAGE/REST. **Not shipped:** the civic-reservation
  mechanism (i) or sink-rate re-tuning (iii) — (ii)+fallback-bias may
  prove sufficient on its own; verify with the audit's own suggested
  5-seed/30k-tick soak before deciding whether (i) is still needed.

- [x] **P0.4 — Voice lines are grammatically broken in 79% of
  dialogue prompts.** Measured 159/201 pack examples: "Ysolde Always
  speaks with measured, deliberate pauses..", "Godfrey He always
  speaks in measured, slow tones..". Root cause,
  `llm/dialogue.py` ~line 362: `voice_bits.append(f"{label}
  {agent.voice}")` — but the mind job authors `voice` as a *complete
  sentence* with its own subject and terminal period. Three-part fix:
  constrain the mind prompt to emit a predicate phrase ("speaks in
  measured, slow tones"); normalize at write time (strip leading
  pronoun/capital, trailing period); and sanitize already-persisted
  voices on load (one-time migration). Small, but it's in *every*
  core-cast dialogue prompt, it costs tokens, and a 2B-class model
  imitates the broken register it's shown.
  **Shipped v1.3.6:** all three parts, except "sanitize on load" is
  implemented as "sanitize on every read" (`normalize_voice_phrase`
  called at the `dialogue.py` consumption site) instead of a one-time
  snapshot migration — functionally equivalent, no migration plumbing
  needed. Known residual: stripping a leading "They" from an
  already-persisted voice can leave a plural-conjugated verb ("Ysolde
  lean on old proverbs" instead of "leans") — cosmetic, and new voices
  won't have this shape since SYSTEM_PROMPT now asks for a bare
  predicate phrase.

## P1 — high-impact quality

- [ ] **P1.1 — Simulation scaffolding leaks into the fiction.** Three
  distinct leaks, one shared fix (a diegetic filter applied to any
  text entering a *speaking* prompt):
  - Raw coordinates: 31/201 dialogue prompts contain "at (x, y)" via
    `grounded_event`, and NPCs dutifully say them — "Remember the
    field at sixty, forty-five?" (verbatim pack example). Translate to
    the nearest place name / "the new field" before prompt insertion,
    or exclude coordinate-bearing categories from dialogue grounding.
  - Memory-fade scaffolding: `faded_memory_text`'s "I only vaguely
    recall:" prefix is quoted *in speech* ("Yeah, I only vaguely
    recall Bartholomew was born to us") and has even been laundered
    into rumor text. Reword as a stage direction the model is told
    never to quote ("(a hazy memory) …"), or move fade into the
    instruction line rather than the memory text itself.
  - Event-text verbatim: `grounded_event` is always
    `recent_events_diverse(...)[0]` — the single most recent diverse
    event, which at current event mix is usually a field planting;
    this is also a top-3 contributor to P0.2's field/soil monoculture
    (the pack's dominant topics are literally "new field", "field",
    "the field"). Pick from the top-5 with category weighting instead
    of `[0]`.

- [ ] **P1.2 — LLM capacity is spent on chatter while cognition
  queues.** Session stats: dialogue 353 + rumor_interpret 149 = 78%
  of successful calls; cognition (the only job that changes behavior)
  is 110. Queue wait p50 is 9.0 s on top of 9.6 s p50 inference —
  end-to-end p95 ≈ 38 s per decision at 8.6 tok/s generation with 3
  concurrent slots. Recommendations: (i) drop `llm_max_concurrent` to
  2 on this hardware — the project's own v0.39 review measured that 2
  streams at ~2× speed beat 3–4 at ~3–4× latency, and
  `n_busy_slots_per_decode` 2.58 says the third slot mostly adds
  contention; (ii) rank scheduling cognition > dialogue >
  rumor_interpret when budget/backpressure rations (dialogue is
  already "most expendable" at the drop stage — apply the same rank at
  the *consume* stage); (iii) P0.2(b)/(c) recover most of the
  rumor_interpret spend for free (shipped — should measurably help
  here too, unverified until a fresh diagnostics read).

- [ ] **P1.3 — Forced-choice cognition still spends a full call.**
  Live example: Fenwick at hunger 0.90 gets "Your current priority is
  obtaining food — there's no real choice about it. Explain briefly…"
  — a 15–18 s, ~310-token call whose *decision* was made
  deterministically before it was sent; only the flavor text is
  LLM-authored. With survival thresholds at 0.6/0.3, a hungry stretch
  converts much of the cognition budget into narration. Cheaper: in
  forced mode, apply the goal immediately and *defer* the in-character
  reason to the agent's next unforced call (or a fallback-pool line) —
  behavior identical, budget freed for open decisions.

- [ ] **P1.4 — The model ignores most supplied context — measure per
  thread, then prune.** Review-pack context-influence: cognition
  reflects *any* supplied context thread in only 44% of outputs and
  synthesizes ≥2 threads in 10%, despite averaging 2.1 threads and
  ~310 prompt tokens. The dialogue side already got the right idea
  (weighted `select_opportunities`, 1–2 threads); cognition still
  sends everything (memories + semantic + mind + beliefs + lesson +
  plan + repair + colocated…). Use the recorder you built: per-thread
  reflected-rate by field, then either rotate threads
  (opportunity-style) or cut the chronically-ignored ones. Fewer,
  sharper threads should *raise* the reflection rate on a small model
  — this is measurable before/after with the exact diagnostics that
  exposed it. (Note: v1.3.5 already shipped a supply-side fix for the
  same underlying diagnostic — see CHANGELOG.md — but hadn't yet
  addressed this pruning angle when this audit was written.)

- [ ] **P1.5 — Duplicate place names.** Live: "Its named places:
  Marshwater; Marshpool; Marshmere; **Marshpool**" — two lakes, same
  name. `_maybe_schedule_geography` never tells the prompt which names
  exist, and `parse_name` doesn't reject collisions. Pass
  `place_names.values()` into the prompt ("already in use: …") and
  fall back on a duplicate parse. Ambiguous place references corrupt
  downstream belief/dialogue grounding that matches on name strings.

- [ ] **P1.6 — Derive cast size from LLM budget, not from a fixed
  count — and tier it.** (Updated after clarification: the intent of
  the cast is to cap LLM load and scale safely with population —
  right goal, wrong control variable.) A fixed `18` is an *input*
  pretending to be a *limit*: at pop 200 it correctly caps load, but
  at pop 24 it means 75% of everyone is LLM-driven and the queue
  saturates anyway, because load is really `cast × jobs-per-agent ÷
  latency`, not cast alone. Make the cap budget-derived and layered:
  - **Size from throughput:** `cast = clamp(sustainable_calls_per_day
    ÷ calls_per_core_agent_per_day, floor, ceiling)` where
    sustainable-calls comes from the measured latency the engine
    already tracks (`llm_prompt_stats`) — on this hardware at ~1
    call/30 s that's ~2,800 calls/day wall-clock ÷ (96-tick sim-day
    pacing) → the number falls out instead of being guessed, and it
    *self-adjusts* when the model or hardware changes. Keep the CLI
    override.
  - **Also cap by fraction:** `min(budget_cast, ceil(pop × 0.4))` so
    a small village keeps a genuine non-core crowd (the crowd is what
    makes the core cast legible).
  - **Tier instead of a binary:** Tier 1 (full minds: cognition +
    dialogue + Reflect/Dream, ~8–10 sticky protagonists chosen by the
    existing `_prominence`/founder logic); Tier 2 (LLM dialogue *only
    when talking to a Tier 1 agent*, deterministic cognition — they
    exist as supporting characters in protagonists' scenes); Tier 3
    (fully deterministic crowd). This concentrates depth where an
    observer is actually looking, scales as O(tier1) rather than
    O(cast), and the noncore_nudge job already proves the
    partial-depth pattern works.
  - **One rotating spotlight slot:** a single Tier-2/3 agent promoted
    to Tier 1 for a season when events implicate them (a death in
    their family, a dispute, a mastery) — cheap narrative focus, and
    it feeds the fine-tune archive a wider variety of minds (§FT.4).

## P2 — real but contained

- [ ] **P2.1 — Ecology is trending empty.** `wildlife_extinct: 34` vs
  `wildlife_recolonized: 6` in 16k ticks, with only 2 hunts — this
  isn't overhunting, it's internal (predator-starvation cascades /
  regen tuning; the log shows a pack starving and scattering). Soak a
  few LLM-off seeds and plot herd/pack counts; if the steady state is
  "empty map," the recolonization pressure or grazer regrowth needs a
  floor. A silent, animal-less world reads as dead to an observer even
  when the numbers are "working."

- [ ] **P2.2 — Disease pressure vs. an unbuildable hospital.** 96
  illness events, 79 recoveries, 10/25 currently ill — the outbreak
  floor is doing its population-valve job, but the counter-lever
  (hospital) is locked behind P0.3's materials starvation. After P0.3
  lands, re-check whether illness prevalence at pop ≤ 30 still sits
  near 40%; if so, scale the outbreak floor by population so small
  villages aren't permanently sick.

- [ ] **P2.3 — Event-feed noise categories.** `surveyor_finding: 296`
  and `terrain_reclaimed: 281` are 16% of all events logged; they
  flood the History tab and (pre-P0.2(d)) the prompts. Batch reclaim
  into one monthly line with a count, and consider demoting
  surveyor findings out of the default feed filter. (Prompt-side
  flooding for `terrain_reclaimed` is fixed by P0.2(d); the UI-feed
  side of this item is still open.)

- [ ] **P2.4 — The settlement belief is frozen and unfalsifiable in
  practice.** "The spring soil is deteriorating" has sat at
  confidence 0.99 through 572 successful plantings; the revision call
  re-emitted it verbatim. Two contributors: the prompt's event slice
  was reclaim-spam (P0.2(d)), and nothing ever presents
  *contradicting* subjective evidence ("another good harvest") as
  such. Cheap fix: when a belief's subject matches a recognizable
  metric family (harvest/soil/food), include one line of recent
  subjective outcome events on that subject in the revision prompt.
  The old review's belief-accuracy metric (§7.4) would make this
  visible on a chart; the metrics harness exists now. (Note: v1.3.4
  already shipped a related fix — `is_noop_belief_revision` stops a
  verbatim-restatement "revision" from being logged/stored — but
  doesn't address the deeper "nothing presents contradicting evidence"
  gap this item describes.)

- [ ] **P2.5 — Town brain rationalizes from belief, not stats.** Live
  call: it sees `materials 1.7/30, 1 structure, 10 ill` and outputs
  "food," citing the soil *belief* as rationale. The objective stats
  are in the prompt but buried at the top, a page above the ask —
  small models weight recency. Move the stat block adjacent to
  "Choose the village's current priority" and ask for the rationale to
  name at least one number. (Keep beliefs in — subjective bias is the
  design — but the *civic instinct* should visibly wrestle with the
  granary, not just the myth.)

## P3 — polish

- [ ] **P3.1 — Recorder status is misleading.** Diagnostics show
  `policy: all_tasks` *and* `sample_rate: 0.1`, and 635 of 643 calls
  were recorded — correct behavior (`sample_rate` only applies under
  the SAMPLED policy, per `recorder._should_record`), but the surfaced
  pair reads like a bug. Omit `sample_rate` from status unless policy
  == sampled.

- [ ] **P3.2 — A verbal tic is spreading across speakers.** "…, and
  so." appears in multiple different agents' lines in the same
  session (it matches one agent's proverb-leaning voice). Likely the
  model imitating a tic it saw in pair-history text; the garbled-line
  filter could flag a tail phrase that appears in >K distinct
  speakers' outputs within a window. Low stakes — but distinct voices
  are the whole point of the voice feature.

- [ ] **P3.3 — Dialogue non-sequiturs.** "Shadows are getting thick
  near Vesna's garden, Ivo." / "Yeah, I only vaguely recall
  Bartholomew was born to us." — line_b frequently answers a
  different conversation. Partly P1.1's leak, partly model class. One
  in-prompt exemplar exchange (good line_a→line_b) is the cheapest
  lever before considering a dialogue-only larger model; you now have
  1,076 archived dialogue examples to fine-tune gemma-4-e2b on, which
  is presumably why the recorder exists — this is its first concrete
  target.

- [ ] **P3.4 — Surface the new failure modes in the dev console.**
  Topic-share (dominant topic %), mood axes, materials
  inflow/outflow, and per-thread context-reflection rate are the four
  numbers this audit needed and had to compute by hand. Each already
  exists server-side or in the archive; one diagnostics block each.

## FT — Fine-tuning roadmap: making gemma-4-e2b-it-qat a Hearthmind
specialist

The recorder's four-layer schema (structured input → prompt → raw
completion → parsed output, with prompt/model versions and hashes) is
already the right substrate — most projects have to retrofit exactly
this. The plan below is ordered; each step gates the next. The single
most important warning first:

> **Do not SFT on the raw archive as-is.** Today's archive is the
> *current un-tuned model's own outputs*, recorded during a run
> exhibiting every P0 flaw above. Training on it is self-distillation:
> the model gets more confidently mediocre — the garden monoculture,
> the "Ysolde Always speaks" grammar, the coordinate-quoting, the
> non-sequitur line_b's all become *learned style*. The archive's
> value right now is (a) a source of real prompts and (b) an eval set
> — not yet a training target.

- [ ] **FT.0 — Ship grammar-constrained decoding first (no training
  needed).** llama-server supports GBNF grammars / `json_schema` per
  request. Every Hearthmind job has a fixed JSON schema — constrain
  decoding to it. This eliminates the entire parse/repair problem
  class at inference time, stops schema tokens wasting the completion
  budget, and (crucially for later) means fine-tuning capacity is
  spent on *content* quality, not on re-teaching JSON syntax a
  grammar enforces for free. One config field per job; measurable
  immediately in `llm_prompt_stats`.

- [ ] **FT.1 — Fix prompts before collecting the real dataset.** Land
  P0.1/P0.2/P0.4 and P1.1 (leaks), then start fresh recording
  sessions tagged with the new prompt versions (the recorder's
  `prompt_versions` + so-far-unused `session_tags` fields exist for
  exactly this). Data collected under broken prompts trains the model
  to cope with brokenness. Treat pre-fix sessions as prompt-corpus
  and eval-only; mark the epoch boundary with a tag. (P0.1/P0.2/P0.4
  shipped in v1.3.6 — P1.1 still open; a real epoch-boundary tag
  should wait until P1.1 lands too.)

- [ ] **FT.2 — Build the quality-label pass (automatic curation).**
  Extend the recorder's `outcome` field (or a post-hoc labeler over
  the archive) with cheap, deterministic per-example labels — every
  one of these already exists as review-pack logic and just needs to
  run per-example: schema-valid; context-reflection score (which
  supplied threads the output references); topic-novelty vs. the
  settlement's dominant topic at that tick; leak flags (regex:
  coordinates, "I only vaguely recall", voice-grammar pattern);
  length-in-bounds; for dialogue, line_b-responds-to-line_a (token
  overlap / question-answered heuristic). The SFT set is then a
  *filter query* over the archive, and the filter thresholds are
  themselves tunable and versioned.

- [ ] **FT.3 — Generate gold targets two ways, both riding the
  archive's replayability:**
  - **Teacher distillation:** replay archived `layer2_prompt`s (and
    fresh prompts regenerated from `layer1_structured_input` — this
    is why storing the structured input was the right call) through a
    much larger model once, offline, to produce reference
    completions. SFT the 2B on (real Hearthmind prompt → teacher
    completion). This is the highest-leverage step for dialogue
    quality (P3.3's non-sequiturs) and for the rare complex tasks
    (beliefs, consciousness, town_brain) where a 2B's reasoning is
    the binding constraint.
  - **Rejection sampling (no teacher needed):** for each prompt,
    sample k=4–8 completions from the *current* model at temperature,
    score with FT.2's labels, keep the best. Cheap, fully local,
    and it also yields (chosen, rejected) pairs — bank those for a
    later DPO pass targeting style failures (tics, non-sequiturs,
    scaffold-quoting) that SFT alone won't fully kill.

- [ ] **FT.4 — Balance the task mix; augment the rare tasks.** The
  archive is dialogue 1,076 / rumor_interpret 475 / cognition 282,
  with the *hardest* structured tasks at 1–6 examples each
  (consciousness 4, town_brain 4, beliefs 5, invention 1). A naive
  mix fine-tunes a dialogue model that's worse at everything else.
  Per-task sampling weights (cap dialogue's share ~30–40%; upweight
  rare tasks), and for the rare ones **synthesize prompts
  programmatically** by perturbing archived structured inputs
  (different stats, moods, belief sets, event mixes) and
  teacher-labeling them — the prompt builders are pure functions, so
  generating 500 diverse town_brain situations is a script, not a
  sim-year of waiting. P1.6's spotlight rotation also widens mind
  diversity in organically collected data (unique-NPC ratio is
  currently 0.04).

- [ ] **FT.5 — Freeze an eval harness before the first training
  run.** You already built the measuring stick — `review_
  diagnostics.py`'s metrics (topic diversity, context-reflection
  rate, multi-thread synthesis, leak counts, parse rate, latency).
  Formalize: a frozen held-out prompt set (deduped by
  `structured_input_hash` against train — the 0.14 duplicate rate
  means dedupe matters; split by hash, never randomly), target
  thresholds per metric, plus ~50 hand-picked golden prompts covering
  every task including the weird cases (forced-choice cognition,
  cross-settlement dialogue, revision-vs-form beliefs). Every
  candidate adapter runs the harness; regressions block adoption.
  Also run a *world-level* A/B: same seed, base vs. tuned adapter,
  compare topic-diversity and belief-accuracy trajectories over 30k
  ticks — the model is being tuned to run a world, so the world is
  the real benchmark.

- [ ] **FT.6 — Train as LoRA on the bf16 base; deploy against the
  QAT quant.** Practicalities for the qat checkpoint: fine-tune LoRA/
  QLoRA adapters on the unquantized base weights (2B trains on very
  modest hardware), evaluate merged-and-requantized *and*
  runtime-adapter variants (llama-server can load a LoRA at launch),
  and keep it **one multi-task adapter**, not per-task adapters — the
  per-job system prompts already act as task tags, and llama-server
  can't cheaply swap adapters per request. Expected data need at this
  scale: ~5–20k *curated* examples across tasks — i.e., a few
  post-fix sessions plus FT.3/FT.4, not months of logging.

- [ ] **FT.7 — Close the loop as a cycle, not an event.** Collect
  (tagged) → label (FT.2) → curate/augment → train → eval (FT.5) →
  deploy adapter → keep recording under a new tag. Version the
