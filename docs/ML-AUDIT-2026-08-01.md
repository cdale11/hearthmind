# Hearthmind — AI/ML vs. LLM Audit and Roadmap

**Filed v1.34.169**, on explicit user instruction: *"Audit the entire
Hearthmind repo (code + docs). Find every current and planned LLM task
and determine if it truly requires an LLM or can be replaced by a
deterministic algorithm or specialized AI/ML... Also identify
deterministic systems with high emergence/sentience potential that
should instead use AI/ML... Do not replace LLMs where language,
creativity, abstraction or ontology expansion genuinely require them."*

## 0. Correction to the v1.34.168 finding

The previous pass (CLAUDE.md, v1.34.168) concluded "nothing in this
codebase should be replaced by a trained model right now." **That
conclusion was too broad and two of its three supporting arguments were
wrong.** Recording the correction explicitly, because the reasoning
error is the kind that would otherwise be repeated:

1. **"A trained classifier is architecturally the same category of
   thing as the deterministic rule system already rejected."** This is
   false. A hand-authored rule system encodes *the developer's* model
   of the world and cannot change. A network trained on the world's own
   accumulated history encodes *that world's* lived statistics and
   changes as the world does — two settlements with different histories
   would produce different models. That is a mechanism *for* emergence,
   not against it. The standing design rule ("don't replace LLM
   reasoning with a large deterministic rule system just because it's
   easier") was written against hand-authored rules and does not reach
   learned models.
2. **"No labeled ground truth exists."** Also false, and directly
   contradicted by this repo's own code. `llm/recorder.py` has recorded
   a four-layer schema since v0.87.28 —
   `layer1_structured_input` → `layer4_parsed_output`, plus
   `latency_ms`, `estimated_prompt_tokens`, `fallback_used`,
   `simulation_tick`, `outcome`. That is a supervised dataset with both
   decision labels and cost labels. The `metrics` table
   (`persistence/database.py:98`) is a second one: a per-tick persisted
   time series.
3. The third argument — *most* `llm/` modules are free-text generation
   a classifier cannot produce — **stands, and still governs the
   majority of the surface.** It just doesn't govern all of it.

## 1. Method and evidence base

Everything below cites real files/lines in this repo. Counted directly:

| Fact | Evidence |
|---|---|
| 56 `_schedule_llm_job(...)` call sites | `simulation/engine.py`, `grep -c` |
| ~45 prompt modules | `hearthmind/llm/` |
| 102 hand-tuned `*_WEIGHT`/`*_LEAN_MAX` scoring constants | `grep -rn` across `hearthmind/` |
| Four-layer per-call training record | `llm/recorder.py:150-200` |
| Per-tick persisted metric time series | `persistence/database.py:98` |
| `Task.cost_hint: float = 1.0` — hand-set, never measured | `simulation/task_graph.py:87` |
| Real measured per-task wall times now exist | `simulation/profiling.py` (`TaskMetrics`, v1.34.167) |
| Closed 7-value goal set | `agents/agent.py:36-48` (`AgentGoal`) |
| External libraries now permitted (v1.34.171, explicit user directive) | `pyproject.toml`'s new `ml` extra |
| 24-module pybind11 C++ extension already shipping | `cpp/src/` |

**Feasibility constraint that shapes every recommendation below,
revised v1.34.171:** the standing §8 decision (v1.34.159) declining a
LoRA training stack is unchanged, but the earlier stdlib-only/no-numpy
constraint on THIS work was self-imposed, not a real environment limit
— confirmed directly (`pip install numpy` succeeds cleanly in this
environment). Explicit user instruction: "allow the use of external
libraries, don't make anything unimplementable just because external
libraries can't be installed." numpy is now a permitted dependency,
gated behind a new optional `ml` extra (`pyproject.toml`) so it never
enters the live server's required dependency set. The shape is now:

> **Train offline** (dev-only `ml` extra, numpy permitted) → **ship
> learned weights as data** (a small JSON/binary blob beside the
> snapshot) → **infer in C++ with a pure-Python (stdlib-only, no numpy)
> fallback**, exactly the pattern all 24 existing native modules
> already follow.

Runtime inference still never depends on numpy or any other external
library — the fallback path stays stdlib-only, same contract as every
native module. Only the offline training path may use numpy (matrix
ops, faster iteration) when that's a genuine win over hand-rolled
Python loops. A 3-layer MLP with a few dozen inputs is a handful of
dot products either way. **The "no training infrastructure" objection
applies to LoRA-fine-tuning a 4B LLM. It does not apply to small
task-specific networks.**

## 2. Part 1 — Every LLM task, classified

Three buckets. The rule applied: **does the output require language,
creativity, abstraction, or ontology expansion?** If yes → LLM stays.
If the output is a bounded choice or a scalar → it is a candidate. If
it is a bounded choice *wrapped in* narration → split it (the pattern
v1.3.35 already established in this codebase five times over).

### 2a. KEEP-LLM — genuinely requires language/creativity/ontology

No ML replacement is possible or desirable. These generate prose,
invent concepts, or expand the shared ontology.

`dialogue`/`voice_dialogue`, `chronicle`, `chronicler`, `folklore`,
`legend`, `letters`, `dream`, `musing`, `omens`, `religion`, `naming`,
`geography`, `world_genesis`, `documentary`, `artifacts`, `summary`,
`sim_summary`, `away_digest`, `culture`/`tradition`, `culture_digest`,
`institution_culture`, `festival`, `caravan`, `diplomacy`,
`composite_entity`, `pillar_chat`, `record`, `mind`,
`narrative_direction`, `skill_mastery`, `memory_drift`,
`rumor_interpret`, `noncore_nudge`.

**Plus the whole ontology-expansion family, which is the single thing
most protected by the project's own design priorities:** `ontology`
(propose/evolve/merge), `invention`, `composite_reaction_propose`,
`rule_propose`, `species_variant`, `nature_mind`,
`nature_causal_reasoning`. These *invent new concepts and name new
categories of thing*. No classifier can produce a genuinely novel
concept — by construction a classifier can only choose among classes it
was trained on, which is exactly the opposite of what
`world/ontology.py`'s registry exists to do. **Do not touch these.**

### 2b. SPLIT — bounded decision + narration, where only the decision moves

This is the highest-value bucket and the pattern this codebase already
uses. v1.3.35 converted five systems this way (geography naming,
era branch, town-brain priority, institution objectives, narrative
direction): *compute the decision deterministically, let the LLM
explain it.* The proposal is to extend that pattern — but with the
decision **learned from the world's own history** rather than
hand-coded.

| Task | Decision component | Narration component | Evidence |
|---|---|---|---|
| **`cognition`** ⭐ | `goal` — one of 7 closed values | `reason` — free text | `llm/cognition.py:90`, `agents/agent.py:36-48` |
| `dispute` | outcome (3 closed outcomes) | the scene itself | `llm/dispute.py` |
| `fission` | leave / stay | why | `llm/fission.py` |
| `migration` | leave / stay | why | `llm/migration.py` |
| `laws` | which hardship becomes law | the law's wording | `llm/laws.py` |
| `guild_founding` | found / don't | the guild's character | `llm/founding.py` |
| `institution_belief` | objective selection | belief text | already partly deterministic (v1.3.35) |

**`cognition` is the flagship.** It is the highest-volume LLM task in
the system (once per core-cast agent per day, the reason the entire
`llm_core_cast_size` budget mechanism exists — see CLAUDE.md's
"swap-after-hours" root cause). Its decision half is a **7-class
classification over a rich, already-assembled feature vector**, and the
recorder has been capturing `(structured_input → parsed goal)` pairs
for every one of those calls for dozens of versions. This is a textbook
imitation-learning target with the dataset already on disk.

**Critically, this does not reduce emergence — it increases it.** Today
the deterministic fallback (`cognition.fallback_goal`) is a hand-written
if-ladder, and it handles the *majority* of goal decisions, because only
the core cast ever reaches the LLM at all. A policy net trained on the
core cast's own LLM-authored decisions would let *the whole
population* act on learned, world-specific, personality-conditioned
judgment instead of a fixed ladder — and would free the LLM budget for
the `reason` text and for the KEEP-LLM jobs. **More agents thinking, not
fewer.**

### 2c. ALREADY CORRECTLY DETERMINISTIC — no change

`town_brain` (decision computed, LLM narrates — v1.3.35), `era_branch`
(same), `faction` (union-find detection, LLM only names it),
`legend_detection` (deterministic pattern match), `self_tuning`
(sandbox-gated numeric). These are already the right shape.

## 3. Part 2 — Deterministic systems that *should* become learned

The user's second question, and the more interesting half. These are
places where a **hand-tuned constant is standing in for a judgment**,
which is precisely where a learned model adds emergence rather than
removing it. All 102 `*_WEIGHT` constants were reviewed; the physical
ones (decay, immune response, fertility, soil) are Body and must stay
deterministic per `docs/CONSTITUTION.md`. These are the cognitive ones.

### 3a. Memory retrieval — the strongest case ⭐

`agents/agent.py:492-535`, `retrieve_relevant_memories`:

```
score = RECENCY_WEIGHT   * recency
      + SALIENCE_WEIGHT  * salience
      + RELEVANCE_WEIGHT * relevance   # relevance = token overlap / 2.0
      + causal bonus
```

This is **already a linear model** — it just has three hand-set weights
(0.5 / 0.3 / 0.5) and a bag-of-words relevance term. Two independent
upgrades:

- **Learn the weights** instead of guessing them. Label: did the
  retrieved memory actually appear (lexically) in the resulting
  cognition output? The recorder already stores both sides.
- **Replace token-overlap with a small learned embedding.** `relevance
  = min(1.0, overlap / 2.0)` cannot see that "the wolves took Bram" and
  "a predator killed my brother" are the same memory. A tiny trained
  embedding (32-64 dims over the sim's own bounded vocabulary) fixes
  this and *directly deepens apparent sentience* — an NPC recalling the
  thematically right memory rather than the lexically overlapping one.

The same token-overlap proxy is used for belief dedup, folklore dedup,
dialogue dedup, and `cognition/pillar.py:60`'s `word_overlap`. **One
learned embedding upgrades all of them at once.**

### 3b. Attention / cognition scheduling ⭐

`cognition/attention.py`: `compute_priority()` is a fixed weighted sum
(salience 0.5 / staleness 0.3 / messages 0.15 / player-focus 0.05).
`Population.core_agent_ids` selection and `_prominence` use another
stack of hand-set weights (`PROMINENCE_BOND_WEIGHT = 4000.0`,
`SKILL_WEIGHT = 2000.0`, `REPUTATION_WEIGHT = 3000.0` —
`agents/population.py:1164-1182`).

These decide **who gets to think**. That is the single highest-leverage
judgment in the whole system, and it is currently four magic numbers.
Learning it against a real objective ("did spending a cognition call on
this agent produce a consequential event?") is a genuine
attention-follows-significance mechanism — and is exactly what B2.4
("attention follows change") asks for and has been blocked on.

### 3c. Social influence / relationship dynamics — GNN territory

`agents/ledger.py` is a real weighted graph (fondness/trust/debt/
grievances per pair). `world/memetics.py`'s `weighted_spread_target`
and `bfs_distances` already run graph algorithms over it. Gossip
contagion, rumor spread, faction formation, and reputation all
propagate on this graph with hand-set coefficients.

This is the natural home for a **small graph neural network**: predict
next-state relationship deltas from local graph neighbourhoods.
Emergence benefit: coalitions and social cascades that arise from
learned structure rather than a fixed contagion constant. This is the
most ambitious item here and should be sequenced last.

### 3d. Belief confidence

`Settlement.beliefs` / `Agent.beliefs` confidence is currently LLM-
asserted, nudged by `phase_g_intensity` and temperament (H8). A learned
calibration model — "given the evidence actually accumulated, how
confident should this belief be?" — would make belief revision track
real lived evidence instead of the model's stated number. Reflection
(`_reevaluate_reflection_hypotheses`) already does a crude version of
this with fixed step sizes.

### 3e. Planning

`Agent.plan` (bounded episodic planning, §7 item 3) is LLM-authored and
then executed by keyword matching in `cognition.fallback_goal`. A
learned plan→action policy (or a small RL policy over the same closed
goal set) would make plans genuinely steer behavior rather than pattern-
match on words.

## 4. Part 3 — Adaptive Runtime (Part B)

**This is the lowest-risk, highest-certainty area in the entire audit**,
because B0's prime invariant already guarantees the runtime never makes
world-meaning decisions. Nothing here can affect emergence by
construction — the worst failure mode is a mis-scheduled task, caught by
`scripts/verify_replay_hash.py`.

| Item | Today | Should be | Why it's safe |
|---|---|---|---|
| **`Task.cost_hint`** ⭐ | hand-set `1.0` (`task_graph.py:87`) | learned from `TaskMetrics.recent_wall_seconds` | B5 already measures it; using the measurement is strictly better than guessing |
| **B8.1 workload forecaster** ⭐ | unbuilt | time-series regression on the `metrics` table | pure prediction; B8.2 reservation is already specced to be non-binding |
| **B7.2 machine profile** | unbuilt | regression: config → measured throughput | `recorder.latency_ms` is the label, already recorded |
| **LLM call cost prediction** | none | regression: `structured_input` → `latency_ms` | lets the scheduler stop issuing a call it can't afford *before* paying for it — directly attacks the `calls_dropped_backpressure` problem in CLAUDE.md's own live reports |
| **B6.2 controller** | bang-bang (shipped v1.34.168) | keep; add B13.5 evolutionary search over tunable sets | already specced, already gated behind B13.2's replay-hash check |

The doc's own B6 text says "deterministic, no LLM — evolutionary
algorithms, statistics, optimization, feedback control." **Statistical
learning is explicitly in scope there; only the LLM is excluded.** The
v1.34.168 reading of that line as excluding ML too was wrong.

## 5. Prioritized implementation plan

Nine stages, ordered by (value × certainty) ÷ risk. Each is
independently shippable and independently revertible. Every stage that
touches simulation behaviour carries a replay-hash gate.

### Stage M0 — Learning substrate *(prerequisite, no behaviour change)*
New `hearthmind/ml/`: a stdlib-only linear/logistic regressor and a
small dense MLP (forward pass + SGD), a fixed feature-vector encoder,
and a versioned weights blob format. Native C++ forward pass added
under `cpp/src/` with the usual pure-Python fallback and randomized-
equivalence verification. **No consumer yet.**
*Benefit:* everything below becomes a small change. *Risk:* none —
inert until used.

### Stage M1 — Runtime cost model *(adaptive runtime, zero emergence risk)*
Learn `Task.cost_hint` from `TaskMetrics`; learn LLM call latency from
`recorder.latency_ms`. Feed both to the B2 scheduler.
*Benefit:* real budget decisions instead of guesses; fewer wasted
backpressure drops. *Risk:* minimal, execution-layer only (B0).

### Stage M2 — Workload forecaster (B8.1)
Time-series regression over the `metrics` table predicting near-term
LLM demand; B8.2 reservation consumes it.
*Benefit:* pre-reserve capacity before a storm/festival spike instead of
reacting after. *Risk:* low; a wrong forecast costs scheduling
efficiency, never correctness.

### Stage M3 — Learned embeddings for the sim's own vocabulary ⭐
Train a small embedding on the accumulated event/memory/belief corpus.
Replace token-overlap in `retrieve_relevant_memories`,
`pillar.word_overlap`, and the four dedup sites.
*Benefit:* the largest *perceived-sentience* gain per unit of work —
NPCs recall thematically right memories. *Risk:* medium; changes
retrieval → changes prompts → changes behaviour. Ship behind a config
flag with A/B comparison.

### Stage M4 — Memory-retrieval weight learning
Replace the three hand-set weights with learned ones.
*Benefit:* retrieval tuned to what actually influenced output. *Risk:*
low, bounded by the same k-slot budget.

### Stage M5 — Cognition goal policy ⭐ *(the flagship)*
Train a 7-class policy on the recorder's `(structured_input → goal)`
pairs. Use it **in place of `fallback_goal`'s if-ladder for the
non-core population**, and as a prior for the core cast. LLM keeps
authoring `reason` for the core cast.
*Benefit:* the whole population acts on learned judgment instead of a
fixed ladder; LLM budget freed for language. *Risk:* highest behavioural
impact of any stage → strictest gate: replay-hash comparison, staged
rollout, config flag, and a hard rule that survival overrides
(critical hunger/energy) remain deterministic and untouched.

### Stage M6 — Attention/priority learning (unblocks B2.4)
Learn `compute_priority`'s weights and the core-cast prominence
weights against "did this cognition call produce a consequential
event?"
*Benefit:* attention genuinely follows significance. *Risk:* medium;
changes who thinks. Gate on population-level outcome metrics.

### Stage M7 — Belief-confidence calibration
Learn confidence from accumulated evidence rather than model assertion.
*Risk:* low — belief content is untouched, only its confidence scalar.

### Stage M8 — Social-graph GNN
Small GNN over `agents/ledger.py`'s pair graph for relationship-delta
and contagion prediction.
*Benefit:* emergent coalitions/cascades. *Risk:* highest complexity;
sequence last, after M0-M3 have proven the substrate.

### Stage M9 — B13.5 evolutionary tunable search
Population-of-configs search over B6's registry, fitness = throughput
under B13.2's replay-hash constraint. Already specced; needs B13.1/2.

## 6. Standing guardrails for all of the above

1. **Never replace ontology expansion, dialogue, or any narrative
   authoring.** A classifier cannot invent a concept; that is the whole
   point of `world/ontology.py`.
2. **Every model is trained on *this world's* history**, and its weights
   are part of world state. Two worlds diverge. That is the feature.
3. **Body stays deterministic** (`docs/CONSTITUTION.md`). No learned
   model may write physics, decay, weather, or resource state.
4. **Replay-hash gate** (`scripts/verify_replay_hash.py`) on every stage
   that touches simulation behaviour; B15's rule holds — a performance
   win that changes outcomes is rejected without a judgment call.
5. **Every model ships with a deterministic fallback**, exactly as every
   native module does. A missing/corrupt weights blob degrades to
   today's behaviour, never to a crash.
6. **External libraries permitted for offline training only, never for
   runtime inference** (revised v1.34.171 — explicit user directive
   relaxed the earlier stdlib-only constraint). Training may use the
   new `ml` optional extra (numpy); the shipped inference path is
   always stdlib + the existing C++ path, so a machine without the
   `ml` extra installed still runs the full simulation unmodified —
   only offline training is affected.

## 7. What this audit did *not* recommend

- Fine-tuning the local LLM (LoRA). Unchanged from v1.34.159 — still
  correctly out of scope, still correctly data-gated by
  `eval_harness.training_readiness_report`.
- Replacing any generative or ontology task.
- A runtime dependency on torch/numpy for inference — training may use
  numpy (v1.34.171), inference never does.
